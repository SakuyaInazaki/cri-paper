# .agent/

这个目录是 agent 在本项目里的工作记忆，也是项目建立过程的记录。两个子目录，分工不同：

- `notes/`：**发生了什么**。每次实质变动一条，按时间顺序，只增不改。答的是「做了什么、为什么」。
- `knowledge/`：**现在相信什么**。政策口径、证据强度、流程约定、缺口。答的是「当前认知是什么、有多确定、依据是哪一句」。可以被推翻，推翻要留痕。

两者的区别：notes 是日志，knowledge 是当前认知。日志不会错，认知会。

## 编号格式（本仓库沿用 chartmaker 那一套）

两个子目录都用同一种格式：

```
NNN-简短主题.md
```

`NNN` 是三位递增编号，从 `001` 起，两个子目录各自独立编号。一个文件对应一条——notes 是一次有实质意义的变动，knowledge 是一个可以独立成立的小点。编号一旦分配就不再回收，删掉的内容用新编号的条目说明，不让旧编号空出来重用。

引用时写「notes 003」「knowledge 002」即可。

（另一种可选格式是 `YYYY-MM-DD-NNNN-主题.md`，把日期放进文件名。本仓库不用它，日期写在文件内的「日期」字段里。）

## notes 条目的字段

- **日期**：变动发生的日期。
- **变更**：这次做了什么，增删改了哪些文件，下了什么决策。
- **理由**：为什么这样做。用户指令就引用户原话要点，agent 自主判断就写判断依据。
- **备选**：还考虑过什么，为什么没选。
- **未做**：这次明确没做的事，以及悬而未决的问题。
- **关联**：相关文件、knowledge 条目、commit。

## knowledge 条目的字段

头部固定这几行：

```
状态：草案 | 候选 | 已采用 | 已推翻
创建：YYYY-MM-DD
最近复核：YYYY-MM-DD
置信度：低 | 中 | 高
来源：报告章节 / 政策原文页 / 用户指令
取代：（被本条推翻的旧条目编号，没有就留空）
被取代：（推翻本条的新条目编号，没有就留空）
```

正文按需写「要点 / 详情 / 依据 / 怎么用」。

## 规则

1. **状态优先于内容。** 读任何条目先看状态。「已推翻」的条目只用来理解当时为什么那样想，不作为依据。
2. **条目可以被推翻，而且推翻是预期会发生的。** 政策每年都改，检测方法每年都变，本仓库的 knowledge 尤其容易过期。发现新证据与旧条目冲突时不许固守旧认知：把旧条目状态改成「已推翻」，写明被什么证据推翻、新条目是哪一条；新条目写明取代了谁。旧条目不删，正文不改，修订记录追加在文末。
3. **每条都要能指回来源。** 政策类的结论写清楚是哪家会议、哪一页、哪句原话，或者本仓库哪份报告的哪一节。二手转述要标明是二手。
4. **不确定就标不确定。** 标了「存疑」的条目不得在别处被当成硬约束使用。
5. **索引要更新。** 新增条目或改状态，都要同步更新本文件下面的两张表。
